# Счётчик подписчиков

`user_afisha_follows` хранит подписки пользователей, `afisha_stats` — готовое число подписчиков каждой афиши. В статистике только `afisha_id` (PK и FK, связь один к одному) и `followers_count` (BigInteger, неотрицательный, по умолчанию 0). Это подписки, не регистрации на мероприятие.

После `poetry run alembic upgrade head` PostgreSQL автоматически:

- создаёт строку статистики при добавлении афиши;
- увеличивает счётчик при фактической вставке подписки;
- уменьшает его при удалении, в том числе при каскадном удалении пользователя;
- корректирует оба счётчика при переносе подписки на другую афишу;
- сбрасывает счётчики при `TRUNCATE user_afisha_follows`;
- удаляет статистику вместе с афишей.

Все изменения выполняются в транзакции исходной операции. Повторная подписка с `ON CONFLICT DO NOTHING` не увеличивает число, повторное удаление отсутствующей связи не уменьшает его. Сервис должен только добавлять/удалять связи — вручную менять счётчик дополнительно нельзя. Прямое редактирование/удаление статистики и отключение триггеров не поддерживаются.

Миграция `20261016_01` создаёт ранее описанную только в ORM таблицу подписок. Миграция `20261016_02` создаёт статистику, один раз подсчитывает уже существующие подписки и устанавливает триггеры. На время заполнения блокируются изменения афиш и подписок; на большой базе миграцию следует планировать отдельно. Если таблица подписок была вручную создана вне Alembic, перед запуском нужна сверка схемы — не удаляйте её ради прохождения миграции.

Для будущей ручки готов сервис `afisha_stats_service` из `src/usecase/afisha/afisha_stats_service.py`. Метод `get_stats_by_afisha_id(afisha_id, session)` возвращает `AfishaStatsResult` с полями `afisha_id` и `followers_count`; если строки нет, выбрасывает `NotFoundError`. В transport остаётся добавить ручку, Pydantic-схему ответа, преобразование DTO в ответ и обработку ошибки как 404. Доменный `AfishaStats` переименован, но для этого простого чтения сервис собирает DTO напрямую из ORM-модели.

При обычном чтении подписки больше не пересчитываются:

```python
followers_count = await session.scalar(
    select(AfishaStatsModel.followers_count).where(
        AfishaStatsModel.afisha_id == afisha_id
    )
)
```

`None` здесь означает отсутствие строки статистики, а не ноль подписчиков. Для загрузки вместе с ORM-моделью используйте `select(AfishaModel).options(selectinload(AfishaModel.stats))`, затем `afisha.stats.followers_count`. Связь read-only и без неявной lazy-загрузки. Если статистика уже была загружена в текущую сессию до изменения подписок, перечитайте её через `await session.refresh(afisha.stats)` или новый запрос со свежими значениями.

`Base.metadata.create_all()` не устанавливает триггеры: нужен Alembic. Ручки подписки и добавление числа в API-ответы этой минимальной реализацией не затрагиваются. При массовых конкурентных изменениях сохраняются обычные правила PostgreSQL: возможны ожидания блокировок и необходимость повторить транзакцию при deadlock.

Проверки: `RUN_AUTH_DB_TESTS=1 poetry run python -m unittest discover -s tests -p test_afisha_stats.py -v`. Они используют отдельные временные PostgreSQL-базы с префиксом `codex_stats_test_`, удаляемые после проверки. Основная база не меняется.
