# Обсуждения концертов — бэкенд

Каждый концерт имеет одно обсуждение. Для запросов используйте UUID концерта
`afisha.id`; отдельный ID чата и поле `reviews_id` не нужны.

## Подключение

- Запуск — по [README](../README.md). В существующем окружении выполните `make migrate`.
- Концерт должен существовать в `afisha`, автор сообщения — в `users`.
- Для отправки используйте `Authorization: Bearer <access_token>` из
  [системы авторизации](auth.md). Допускаются роли `user` и `admin`.

Концерты и пользователей создают соответствующие модули. Обсуждение проверяет
их наличие в БД.

## API

Базовый адрес при стандартном запуске: `http://localhost:8080`.
Описание схем доступно в `/docs`.

| Запрос | Доступ | Ответ |
| --- | --- | --- |
| `GET /api/afisha/{afisha_id}/messages` | Всем, без токена | `200`, страница сообщений |
| `POST /api/afisha/{afisha_id}/messages` | Авторизованным, включая администратора | `201`, сохраненное сообщение |

### Загрузка истории

GET возвращает **последние 50 сообщений** по умолчанию. Параметр `limit` задает
размер страницы от 1 до 100. Внутри страницы сообщения идут от старых к новым,
с сортировкой по `created_at`, затем `id`.

```http
GET /api/afisha/{afisha_id}/messages?limit=50
GET /api/afisha/{afisha_id}/messages?limit=50&before=<next_cursor>
```

Ответ содержит `items`, `next_cursor` и `has_more`. Для загрузки более ранних
сообщений передавайте полученный `next_cursor` в `before` без изменений.
Курсор работает только для своего концерта. Новые сообщения не сдвигают
ранее полученную границу истории.

Когда более ранних сообщений нет, `has_more` равен `false`, а `next_cursor` — `null`.
Пустая история возвращается так:

```json
{"items": [], "next_cursor": null, "has_more": false}
```

### Отправка

POST принимает только `text`: строку длиной 1–2000 символов после удаления пробелов
по краям. Пустой текст и дополнительные поля запрещены. Автор берется из JWT;
`author_id`, ID сообщения и время создания передавать не нужно.

```http
POST /api/afisha/{afisha_id}/messages
Authorization: Bearer <JWT>
Content-Type: application/json

{"text": "Кто собирается на концерт?"}
```

Формат сообщения одинаков для ответа POST и элементов `items` в GET:

```json
{
  "id": "33333333-3333-4333-8333-333333333333",
  "afisha_id": "11111111-1111-4111-8111-111111111111",
  "author_id": "22222222-2222-4222-8222-222222222222",
  "nickname": "listener_1",
  "text": "Кто собирается на концерт?",
  "created_at": "2026-10-14T15:00:00Z"
}
```

Время возвращается в UTC. `nickname` — имя автора из таблицы пользователей;
оно возвращается сразу в истории, без ожидания WebSocket-уведомлений.

| Ошибка | Причина |
| --- | --- |
| `401` | Нет действительного токена или его пользователь отсутствует в БД |
| `404` | Концерт отсутствует в БД |
| `422` | Некорректный UUID, тело запроса, `limit` или `before` (включая курсор другого концерта) |

## Уведомления о новых сообщениях

Подключитесь к `ws://localhost:8080/api/ws` (через HTTPS — `wss://<host>/api/ws`).
Подписка публичная: токен не нужен. Отправка сообщений остается через POST.

После ответа `{"type":"connected","connection_id":"..."}` подпишитесь на концерт:

```json
{"action": "switch_afisha", "afisha_id": "11111111-1111-4111-8111-111111111111"}
```

Ответ `{"type":"subscribed","afisha_id":"..."}` подтверждает подписку.
После него загрузите историю через GET. Новое сохраненное сообщение вызывает
уведомление только подписчикам этого концерта, включая автора, если он подписан:

```json
{"n_type": 2, "text": "Кто собирается на концерт?", "user_id": "22222222-2222-4222-8222-222222222222", "nickname": "listener_1"}
```

Это сигнал для обновления истории через GET без `before`; полные сообщения с ID
и временем возвращает HTTP API. Объединяйте их по `id`. После переподключения
повторите подписку и чтение истории; большой пропуск можно догрузить пагинацией.

`{"action":"leave_to_main_menu"}` снимает подписку и возвращает
`{"type":"unsubscribed"}`. Для поддержания соединения отправляйте
`{"action":"ping"}` примерно раз в 30 секунд; ответ — `{"type":"pong"}`.
Некорректная команда подписки получает `{"type":"error","message":"..."}`.

Уведомление отправляется после commit. Ошибка рассылки не отменяет сохранение и
ответ `201`; история остается доступной через GET. Рассылка сейчас работает
между соединениями одного процесса приложения; для нескольких workers нужна
отдельная доставка событий через Redis Pub/Sub.

## Хранение и ограничения

Сообщения хранятся в PostgreSQL, в таблице `discussion_messages`, с внешними ключами
на `afisha.id` и `users.id`. Физическое удаление концерта или автора, имеющего
сообщения, запрещено (`ON DELETE RESTRICT`). Отмена концерта сохраняет обсуждение.

Удаление сообщений пока не реализовано. Поле `deleted_at`
подготовлено для мягкого удаления; помеченные записи возвращаются с текстом
«Сообщение удалено».
